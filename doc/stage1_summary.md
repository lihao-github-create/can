## 1. CAN、BLF 和 DBC 的关系

- **CAN**：车上 ECU 之间使用的一种总线通信协议。
- **BLF**：保存采集到的总线数据的二进制日志格式。
- **DBC**：描述报文中信号的位置、长度和换算规则，用于解释原始数据。

```text
实车 CAN 总线 → 采集设备 → BLF → CAN ID 和原始字节
                                           ↓ 结合对应 DBC
                                      车速、角度等信号
```

本阶段只进行到读取、统计和观察原始字节。

## 2. 环境与第一次读取

本次使用 Python 3 和已经安装的 `python-can`，代码中通过 `import can` 导入。练习文件为：

```text
data/Logging_22026-10-16_13-37-18.blf
```

下面的命令和后续脚本均在项目根目录运行。脚本中的相对数据路径以终端当前工作目录为基准。

```bash
python3 - <<'PY'
from itertools import islice
import can

with can.BLFReader("data/Logging_22026-10-16_13-37-18.blf") as log:
    for msg in islice(log, 5):
        print(msg)
PY
```

- `BLFReader` 逐条读取报文。
- `with` 在读取结束后关闭文件。
- `islice(log, 5)` 只取前五条，避免一次输出整个日志。

## 3. 识别一条报文

本次文件的第一条输出为：

```text
Timestamp: 1792157838.325893    ID: 236    S Rx    F BS    DL: 8
3b cf 1f 0f f0 03 01 00    Channel: 1
```

| 字段 | 含义 |
|---|---|
| `Timestamp` | Unix 时间戳，单位为秒，不是从日志开始算起的秒数 |
| `ID: 236` | 十六进制 CAN ID，即 `0x236`；不能直接当作 ECU 地址 |
| `S` | 标准帧，使用 11 位 CAN ID；标准/扩展描述的是 ID 格式 |
| `Rx` / `Tx` | 相对于记录设备或工具的接收/发送方向 |
| `F` | CAN FD 报文 |
| `BS` | 启用了比特率切换 |
| `DL: 8` | 此处显示的数据长度为 8 字节 |
| `Data` | 原始数据，每两位十六进制数表示一个字节 |
| `Channel: 1` | 读取器显示的通道编号 |

字节位置从 0 开始计数：

```text
位置：Byte 0  Byte 1  Byte 2  Byte 3  Byte 4  Byte 5  Byte 6  Byte 7
数据：  3b      cf      1f      0f      f0      03      01      00
```

注意：

- 数据里的 `10` 表示十六进制 `0x10`，对应十进制 16。
- `0x0D0` 和 `0xD0` 是同一个数值，前导零不改变 ID。
- 经典 CAN 数据最多 8 字节；CAN FD 可以超过 8 字节，本次已经观察到 16 字节报文。
- DLC 是长度编码，不能在 CAN FD 中总是直接当作字节数。查看实际数据字节数可使用 `len(msg.data)`。
- “标准帧”不等于“经典 CAN”：本次输出中的 `S` 和 `F` 可以同时出现。

## 4. 用 Python 单独读取字段

| 表达式 | 用途 |
|---|---|
| `msg.timestamp` | 获取时间戳，单位为秒 |
| `msg.channel` | 获取通道编号 |
| `msg.arbitration_id` | 获取 CAN ID 的整数值 |
| `msg.is_extended_id` | 判断是否使用扩展 ID |
| `len(msg.data)` | 获取实际数据字节数 |
| `msg.data.hex(' ')` | 将数据按十六进制显示，用空格分隔字节 |
| `f"0x{msg.arbitration_id:03X}"` | 将 ID 显示为至少三位的大写十六进制 |

两种常用时间计算方式：

```python
elapsed = msg.timestamp - first_time
interval_ms = (msg.timestamp - previous_time) * 1000
```

`elapsed` 是相对于选定起点的秒数；`interval_ms` 是与上一条报文的间隔，单位为毫秒。先筛选再计算时，比较的就是相邻两条匹配报文。

例如，`0.000133 s` 等于 `0.133 ms`，也就是 `133 μs`。

## 5. 统计整个文件的通道和 ID

脚本：[can_parser.py](../exercises/stage1/can_parser.py)

```bash
python3 exercises/stage1/can_parser.py
```

该脚本遍历整个文件，跳过错误帧，按通道计数，并按 `(CAN ID, 是否扩展帧)` 分别统计。当前统计没有排除远程帧。

本次运行结果：

| 通道 | 报文数量 | 不同 ID 数量（区分标准/扩展） |
|---|---:|---:|
| 1 | 70,111 | 167 |
| 2 | 59,215 | 74 |
| 3 | 62,930 | 90 |
| 合计 | 192,256 | 不直接相加作为全文件去重数量 |

统计中的关键概念：

- `Counter` 用于计数，遇到一次对应项就加 1。
- `defaultdict(Counter)` 为每个通道分别保存一组 ID 计数。
- 某个 ID 有 1000 条报文，表示出现了 1000 次，不是有 1000 个不同 ID。
- 同一个 ID 可以出现在多个通道中，观察时需要同时确定通道和 ID。
- 各通道 ID 数量之和不是整个文件去重后的 ID 数量。

## 6. 筛选一个 ID，观察间隔与数据变化

脚本：[watch_id.py](../exercises/stage1/watch_id.py)

```bash
python3 exercises/stage1/watch_id.py
```

通过以下变量选择目标，脚本当前设置为通道 1 的 `0x0B4`：

```python
target_channel = 1
target_id = 0x0B4
```

脚本跳过错误帧、远程帧和不符合条件的报文，只观察目标标准帧的前 20 条。`continue` 表示跳过当前报文，`break` 表示结束循环。相对时间从第一条匹配报文开始计算。

### 实验一：通道 1，ID `0x236`

将 `target_id` 设置为 `0x236` 后，观察到：

- 相邻间隔约 50 ms，对应每秒约 20 条。
- 本次 19 个间隔在 49.351～50.786 ms 之间。
- 前 20 条的 8 个数据字节全部相同：`3b cf 1f 0f f0 03 01 00`。
- 这只说明当前样本中的数据没有变化，不能推断整个文件都不变。

### 实验二：通道 1，ID `0x0B4`

将 `target_id` 设置为 `0x0B4` 后，观察到：

- 相邻间隔约 10 ms，对应每秒约 100 条。
- Byte 0、Byte 1 变化；Byte 2～Byte 7 在样本中保持 `00 5f 00 00 ff ff`。
- Byte 1 呈现以下循环规律：

```text
07 → 08 → 09 → 0a → 0b → 0c → 0d → 0e
   → 00 → 01 → 02 → 03 → 04 → 05 → 06 → 07 …
```

本次输出中从 `0e` 回到了 `00`，没有出现 `0f`。当 Byte 1 再次到达 `07` 时，整条数据也回到了 `06 07 00 5f 00 00 ff ff`。

以上是样本中的观察结果。不能仅凭变化规律确定哪个字节是计数器、校验值或物理信号，也不能把观察到的约 10 ms 或 50 ms 直接当成协议规定的发送周期。
